# 規格：發送對象支援「多人（上傳名單）」+ 個人模式手動輸入號碼

狀態：**規格草案，待使用者確認後才進入實作（三 agent 鐵律流程，本功能複雜度預估為
「複雜」等級 —— 多檔、跨模組、CI-critical、有分支與 I/O，QA 20+ case、一定派
code-reviewer）**。本檔只是規格文件（不是程式碼），依專案慣例可由主 Claude 直接寫，
不受 `writer-qa-iron-rule` 限制。

## 背景

`GET /` 表單頁目前「發送對象」欄位是**互斥**的兩種模式（見 `web/templates.py`
`_recipient_field`）：有設 `MITAKE_WEB_RECIPIENTS_PATH` 名單就**只給下拉選單**，
沒設或名單是空的才**只給手動輸入號碼**。整條發送流程（token、確認頁、成功/失敗頁、
稽核紀錄、速率限制）都是圍繞「一次送一個人」設計的。

使用者這次要的三件事：

1. 發送對象可以是「一個人」或「一群人」。
2. 一個人模式：下拉選單旁**同時**提供手動輸入號碼欄位（現況是二選一，改成並存）。
3. 一群人模式：上傳 `.txt` 檔（每行一支手機號碼，檔案內只有號碼），送出後同一則
   內容發給檔案裡的每一支號碼。

三個決策已與使用者確認：

- **名單輸入走真正的檔案上傳**（`<input type="file">` + `multipart/form-data`），
  不走「貼上文字框」的簡化路線。專案目前是純標準庫、零依賴，`http.server`
  沒有內建 multipart 解析，這塊需要自己刻一個小型解析器（新增攻擊面，見下方
  「安全性」）。
- **群發沿用現有的每小時則數上限**（`DEFAULT_RATE_LIMIT_SEGMENTS = 20`）。超過
  就整批擋下、要求分批送，不另開一組較高上限。
- **名單裡的無效格式／重複號碼一律跳過**，不整批拒收；跳過的號碼與原因會列在
  確認頁，操作者按下送出前能看到完整名單再決定。

## 目標

- 個人模式：`GET /` 表單頁同時提供「從名單選」下拉與「手動輸入號碼」文字欄，
  兩者擇一使用；伺服器端仍以「只信一個來源」為準，不做模糊的優先序猜測。
- 多人模式：上傳 `.txt` 檔 → 伺服器端解析、驗證、去重、分類 → 確認頁列出
  「將發送 N 人／跳過 M 人（含原因）／共扣 N×則數 點」→ 按下送出 → 逐一呼叫
  `mitake.send_sms()`（三竹沒有批次 API，只能迴圈打 N 次）→ 逐筆結果頁（成功／
  未扣點失敗可重送／未確認請勿重送，各自列出遮罩號碼）。
- 全程維持專案既有鐵律：二階段確認、一次性 token、`possibly_charged` 分流、
  絕不讓「可能已扣點」與「確定沒扣點」混在同一種畫面語氣裡。

## 使用者可見的 UI 變化

`GET /` 表單頁「發送對象」區塊改版：

1. 最上層加一組模式切換（radio：「個人」／「多人（上傳名單）」，預設「個人」）。
   純前端切換要不要顯示哪個子區塊，沿用現有 `_SEGMENT_SCRIPT` 同一顆
   `<script nonce>`（CSP 相容，不新增 inline handler）。
2. **個人模式**子區塊：
   - 有名單時：既有下拉選單（`_recipient_field` 現有邏輯）**+** 新增一個
     「或手動輸入號碼」的 `<input type="tel">`。
   - 沒名單時：只有手動輸入欄（與現況完全一致）。
   - 下拉與手動輸入若**同時**有值 → 視為輸入衝突，`/preview` 直接擋下、
     不猜優先序（理由見下方「核心邏輯 §2」）。
3. **多人模式**子區塊：一個 `<input type="file" accept=".txt">`，說明文字寫清楚
   「純文字檔，每行一支手機號碼，檔案內不要有其他內容」。
4. 訊息範本 radio 與簡訊內容 textarea 兩種模式共用（同一則內容發給所有人）。
5. 確認頁（`/preview` 的回應）依模式分流：
   - 個人模式：沿用現有 `render_preview`（單一號碼／收件人姓名）。
   - 多人模式：新的 `render_preview_batch`——列出「將發送 N 人」（可摺疊列表，
     每支號碼遮罩顯示）、「跳過 M 人」（號碼遮罩 + 跳過原因：格式錯／重複）、
     「共 N 人 × M 則 = 扣 N×M 點」。
6. 送出後的結果頁（`/send` 的回應）也分流：
   - 個人模式：沿用現有 `render_sent` / `render_failed_safe` /
     `render_failed_unconfirmed`。
   - 多人模式：新的 `render_batch_result`——三個分組（✅ 已送達三竹 N 筆／
     ❌ 未扣點失敗 N 筆，可重送這幾筆／⚠️ 未確認 N 筆，請勿對這幾筆重送），
     每筆列遮罩號碼 + msgid（有的話）。**這頁同樣不可以有任何一鍵重送整批的
     按鈕**——重送的對象只能是「未扣點失敗」那組，且必須重新走一次確認頁
     （見下方「核心邏輯 §6」）。

## 核心邏輯

### §1 multipart/form-data 解析（新增：`web/multipart.py`，純標準庫）

- 只解析本功能需要的最小子集：從 `Content-Type: multipart/form-data;
  boundary=...` 取出 boundary，依 boundary 切段，每段解析 `Content-Disposition`
  的 `name` / `filename`，回傳 `dict[str, list[str]]`（純文字欄位，沿用既有
  `Mapping[str, Sequence[str]]` 形狀，不改動下游 handler 的介面）+ 檔案欄位另外
  用 `dict[str, bytes]` 回傳（因為檔案內容要當 UTF-8 文字解析，不宜跟一般表單
  欄位混在同一個 dict）。
- `web/server.py` 的請求分派層依 `Content-Type` 前綴判斷：
  `application/x-www-form-urlencoded` 走現有 `parse_qs` 路徑，
  `multipart/form-data` 走新解析器；其餘一律 400。
- 上傳大小另開一個較高的位元組上限常數（現有 `MAX_REQUEST_BODY_BYTES = 64KB`
  是給一般表單用的，不夠放名單檔），只在 multipart 請求時套用；一般表單請求
  仍是 64KB，不放寬。具體數字待實作時依「預期最大名單筆數」（例如 2000 支
  號碼 × 每行約 12 bytes ≈ 24KB，抓幾倍安全係數）敲定。
- 解析失敗（缺 boundary、段落格式不符、非 UTF-8 內容）一律回 400，不 500、
  不嘗試「盡量解析」——這是全新程式碼，錯誤時保守拒絕優於猜測。

### §2 個人模式：下拉與手動輸入衝突判斷

沿用專案既有「輸入來源衝突就整個擋下，不猜」的風格（同 `web/recipients.py`
`RecipientBook.get()` 對 ambiguous id 的處理）：

- 下拉有選、手動輸入為空 → 現有邏輯（以 `recipient_id` 反查號碼）。
- 手動輸入有值、下拉未選（或選了佔位選項）→ 現有邏輯（以 `phone` 欄位為準，
  過 `mitake.validate_phone`）。
- **兩者都有值** → `/preview` 回 400，訊息明講「下拉選單與手動輸入號碼請只
  擇一，已清空、請重新填寫」，不送出、不扣點。理由：若默默選其中一個當優先，
  使用者會以為送去的是他手動打的那支、實際卻送到下拉選的人（或反過來），
  這正是本專案要不惜代價避免的「畫面與實際不一致」。
- 兩者都空 → 沿用現有「必須選一個」的錯誤訊息。

### §3 多人模式：名單解析與分類

輸入：上傳的 `.txt` 內容（bytes → UTF-8 解碼，解碼失敗直接 400「檔案編碼有誤，
請存成 UTF-8 純文字檔」）。

處理步驟（純函式，可離線單元測試，仿 §1 的「純解析、不碰 I/O」風格）：

1. 依行分割，去除每行前後空白，空行跳過。
2. 逐行呼叫 `mitake.validate_phone()`；擋下的（格式錯、非 09 開頭、長度不對）
   歸入「跳過：格式錯誤」，附上原始行內容（遮罩後）方便操作者回頭核對原始檔案。
3. 對通過驗證的號碼去重（同一支號碼在檔案裡出現兩次以上，只留第一次出現的，
   其餘歸入「跳過：重複」）。
4. 名單為空、或去重驗證後有效號碼數為 0 → `/preview` 回 400「檔案中沒有可發送
   的有效號碼」，不產生 token。
5. 有效號碼數超過一個上限（待定，例如 500 筆——不是速率上限，是防止單一 token
   或稽核紀錄無限膨脹的合理性上限）→ 400「單次名單不可超過 N 筆，請分批上傳」。

### §4 確認頁與 token／速率限制的延伸

- `PendingSend`（`web/server.py`）需要能表達「一組收件人」而不只是一支電話：
  新增一個批次專用的資料結構（例如 `PendingBatchSend`，持有
  `list[str]`（有效號碼）+ `body` + `segments` + `chars`），或是把
  `PendingSend.phone: str` 擴充成 `phones: list[str]`（單人送出時 list 長度為
  1）。兩種做法都可行，實作時再依現有測試相容性選一種，這裡先只釘住語意：
  **token 存的是「一組要送的號碼」，前端拿不到、也改不了這組號碼。**
- 速率限制：`/preview` 用 `self._rate.check(len(phones) * segments)`（沿用
  「先檢查不佔用」的既有語意，只是 cost 從 `segments` 換成
  `len(phones) * segments`）。超過上限的錯誤訊息需要講清楚「N 人 × M 則 =
  共 N×M 則，超過本小時上限」，不是只講單一數字。
- `/send` 用 `self._rate.reserve(len(phones) * segments)` 一次性預約整批的
  額度；迴圈送完後，依實際「確定沒扣點」的筆數計算要退還多少（見 §5），呼叫
  `release` 時只退那一部分，不是全有全無。

### §5 送出迴圈與 `possibly_charged` 語意延伸

這是整個功能最核心、風險最高的一段，因為它把「單一結果的二選一畫面」變成
「N 個獨立結果的列表」：

1. 依序（不平行，避免短時間內大量打三竹 API 被限流——那會連個人模式的發送
   一起壞掉，見 `StatusQueryThrottle` docstring 同樣的顧慮）對每支號碼呼叫
   `mitake.send_sms(phone, body, max_segments=..., timeout=...)`。
2. 每筆呼叫的結果分三類，比照現有的 `possibly_charged` 判斷：
   - **成功**（`MitakeAPIError` 沒發生）→ 歸入「已送達三竹」，記下 msgid。
   - **確定沒扣點失敗**（`MitakeValidationError` / `MitakeAPIError` 且
     `possibly_charged=False`）→ 歸入「未扣點失敗」，記下原因。
   - **可能已扣點**（`MitakeAPIError` 且 `possibly_charged=True`，或未預期例外）
     → 歸入「未確認」，記下 msgid（若有）。
3. 每筆呼叫前後都寫一筆稽核紀錄（`AuditLog.record_attempt` /
   `record_result`，比照現有單筆流程），額外帶一個 `batch_id`（本次批次的
   uuid，issue token 時產生）欄位，讓事後在 `send-audit.jsonl` 裡能用
   `batch_id` 把同一批的 N 筆記錄串起來。
4. 迴圈跑完後計算「確定沒扣點」的則數總和，向 `RateLimiter.release()` 退還
   對應額度；「已送達」與「未確認」的則數視為已消耗，不退。
5. 若送到一半 process 被中斷（VPS 重啟／崩潰）：已送出的那幾筆稽核紀錄留底
   （`record_attempt` 已在送出前寫入），但**這次不做「續傳未送完名單」的機制
   ——那是明確的 MVP 範圍外**（見「已知限制」）。操作者需要自行核對稽核紀錄，
   找出還沒送的號碼，手動重新上傳一份只含剩餘號碼的名單。

### §6 批次結果頁的「重送」規則

- 「未扣點失敗」那組**可以**重送，但不是一個按鈕重送整批——而是把這組號碼
  重新組成一份新名單，導回 `/preview`（走全新的確認頁 + 全新 token），
  與現有 `_hidden_resend_form` 對單人重送的邏輯同一個精神：**永遠重新確認，
  不give 一鍵直接花錢的按鈕**。
- 「未確認」那組**沒有任何送出/重送入口**，只列出號碼與 msgid，提示操作者
  去三竹後台逐筆查證——與現有 `render_failed_unconfirmed` 同一條鐵律
  （這頁不可以有 `<form>`）。
- 「已送達」那組純顯示，不提供任何動作。

## 邊界條件

- 上傳空檔案 → 400，不產生 token。
- 上傳非 `.txt`（例如誤傳 `.xlsx`）→ 檔名副檔名檢查只是提示用（前端
  `accept=".txt"` 擋不住的一定要伺服器端再擋一次）；伺服器端實際判斷依內容能否
  以 UTF-8 解碼、且解析出至少一個有效號碼，副檔名不符但內容剛好是純文字號碼清單
  時**允許通過**（不然使用者把檔名打錯就整個卡住，且副檔名本來就是前端可偽造
  的東西，不該當成安全邊界）。
- 名單全部無效（例如貼成 Excel 匯出帶標題列的檔案）→ 400，列出前幾行實際讀到
  的內容（遮罩後）方便操作者判斷「是不是選錯檔案」。
- 名單筆數 × 則數剛好等於速率上限 → 允許（`<=` 而非 `<`，沿用
  `RateLimiter._check_locked` 現有語意）。
- 個人模式手動輸入的號碼格式錯 → 沿用現有 `mitake.MitakeValidationError`
  錯誤訊息與回填行為，不受本次改動影響。
- 上傳請求的 Content-Length 超過批次專用上限 → 400，不嘗試部分讀取。

## 安全性

- multipart 解析器是全新程式碼，需要比照 `web/templates.py` 開頭那條規則
  （任何進 HTML 的輸入都過 `html.escape`）：解析出來的每一行號碼在確認頁／
  結果頁顯示前，一律走現有的 `_e()` 跳脫（本來就會，因為最終渲染都經過
  `templates.py`），這裡特別注意的是**解析器本身**要防禦畸形 multipart
  body（缺 boundary、boundary 在內容裡重複出現、超長單一段落）不能讓解析器
  自己掛掉或吃光記憶體——上傳大小上限就是為此設的第一道防線。
- 檔案內容一律當「不可信輸入」：不因為「使用者是自己人」就放寬驗證，每一支
  號碼照樣過 `mitake.validate_phone()`，不因為「看起來像手機號碼」就放行。
- CSP 不受影響：新的模式切換沿用既有 nonce 腳本機制，不新增 inline handler、
  不新增外部資源。

## 依賴

- 無新第三方套件（`web/multipart.py` 純標準庫）。
- 沿用 `mitake.py` 既有的 `validate_phone` / `send_sms`，不修改 `mitake.py`。

## 已知限制（MVP 刻意不做，之後有需要再補）

- **不支援「續傳未送完的批次」**：process 中斷後，剩餘號碼由操作者自行對照
  稽核紀錄手動重新上傳。
- **不支援批次跨小時分批自動排隊**：撞速率上限時要求操作者自行分批重新上傳，
  不做「先送 20 則、等下一個時段自動送剩下」的排程機制。
- **不支援 CSV／Excel 名單**：只吃純文字、一行一支號碼；有其他格式需求時
  再擴充解析器。
- **不做「同一批次內有人已經是舊名單的今日重複收件人」的跨批查重**：批次內
  自己去重，但不查「這支號碼今天稍早是不是已經在別的批次或單筆發送裡發過同一
  類訊息」——那是更高階的行銷防打擾邏輯，不在本次範圍。

## 分階段實作順序（對照三 agent 鐵律要跑的檔案）

1. `web/multipart.py`（新檔）——multipart 解析，純函式、無 I/O，先寫先測。
2. `web/batch_recipients.py`（新檔，或併入 `web/recipients.py`）——名單解析、
   驗證、去重、分類，純函式、無 I/O。
3. `web/templates.py`——模式切換 UI、`render_preview_batch`、
   `render_batch_result`。
4. `web/server.py`——請求分派層支援 multipart、`PendingSend`／批次資料結構、
   `handle_preview` / `handle_send` 分流邏輯、速率限制與稽核延伸。
5. `web/audit.py`——`batch_id` 欄位（若現有 API 需要擴充參數）。
6. 測試：純函式（§1 §3）先跑到位，再補 `handle_preview` / `handle_send`
   的批次分支整合測試（含「部分成功部分失敗」的假 sender 場景）。
